## Summary

The listed code findings are fixed and were verified by reading the authorization/query paths and by running lint and production build. Owner detail/edit queries now also filter by `ownerId`; unit mutations authenticate before lookup and scope OWNER queries through property ownership. Public registration and invitation acceptance retain validation and use the existing in-memory limiter.

Additional hardening: [next.config.ts](next.config.ts#L28) sets the requested response headers. Owner property detail and edit lookups are scoped in-query at [src/app/(dashboard)/owner/properties/[id]/page.tsx](src/app/(dashboard)/owner/properties/[id]/page.tsx#L21) and [src/app/(dashboard)/owner/properties/[id]/edit/page.tsx](src/app/(dashboard)/owner/properties/[id]/edit/page.tsx#L18). Exported public bootstrap/login/invitation actions are intentionally public and use validation and rate limits; `isRegistrationOpen` returns only bootstrap availability.

## Manual follow-ups

- In the Supabase dashboard, configure the `property-images` bucket with a 5 MB file size limit and allowed MIME types `image/jpeg`, `image/png`, and `image/webp`. Signed upload URLs do not enforce these limits by themselves.
- Replace the in-memory rate limiter with Upstash Redis for distributed/serverless multi-instance support; this remains a TODO in [src/lib/rate-limit.ts](src/lib/rate-limit.ts#L3).
